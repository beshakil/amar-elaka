## 2. Phase 1 selection

Phase 1 enables one category per platform pillar in CLAUDE.md. Each one has
simple fields, can be seeded on day one, and doesn't need a module we haven't
built yet:

| Pillar            | Category               | Why this one first                                                                                                                                                                                                                   |
| ----------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Marketplace       | `buy-sell`             | General classifieds carry the most volume. Its children stay off in phase 1, so everything goes into the general category with the shared fields. Phones will land here, so `buy-sell` is **`pre` at category level** (decision Q6). |
| Rental            | `to-let`               | The most common local need, and "to-let" is already a household word. Its fields are the most structured and the most useful for filtering. It also earns credit revenue from day one.                                               |
| Service           | `on-demand-service`    | Covers the "service platform" pillar. `lead_fee` isn't billable yet (schema change C6), so it runs **effectively free** in phase 1, which helps build provider supply.                                                               |
| Directory         | `local-shop-directory` | Solves the cold start: agents survey shops before launch, so the app has content on day one without depending on users posting. Claimed shops lead to store subscriptions later.                                                     |
| Local information | `emergency-numbers`    | Works without login, is seeded by staff and agents, carries no user-content risk, and builds trust. Uses the `module` kind (C2), so tenants enable and order it like any other tile.                                                 |

Mechanics: phase-1 categories are seeded `is_active = true`. All the others are
seeded `is_active = false` with their schema **published**, so turning one on
later is a data change, not a deploy. Tenant provisioning inserts
`tenant_categories` rows only for active categories (schema §3.5).

Phase 1 has three pre-moderated categories: `to-let`, `on-demand-service` and
`buy-sell`. Partners need moderators in place from launch. Tenants can't loosen
a category-level `pre` (schema §3.5); if moderation proves too slow, the
platform changes the category default.

## 3. How this maps to the schema

### 3.1 Kinds and backing

| backing | table                                      | kinds                             | custom fields live in                                |
| ------- | ------------------------------------------ | --------------------------------- | ---------------------------------------------------- |
| posts   | `posts.fields`                             | marketplace, rental, service, job | `category_field_schemas` (versioned, §13.13)         |
| places  | `places.fields`                            | place                             | `category_field_schemas`                             |
| module  | `emergency_contacts`, `blood_*`, `bazar_*` | `module` (new, C2)                | **the table's own columns**. No custom-field schema. |

Every post and place already has columns for these, so **no category repeats
them as a custom field**:

- **Posts:** `title`, `description`, photos (`media_attachments`), `location`/`locality_id`, `price_type_code` (fixed / negotiable / free / on_request / per_hour / per_day / per_month), contact phone (`contact_phone_e164`, only revealed through `reveal_contact_phone()`), `show_phone`, `allow_chat`.
- **Places:** `name_bn`, `name_en`, `description`, `phones[]`, `website_url`, `facebook_url`, `address_text`, `location`, opening hours (`place_hours`, including overnight hours and a Jummah break).

### 3.2 Field types → JSON Schema

| spec type     | JSON Schema                                                                    | notes                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `text`        | `string`, `maxLength`, optional `pattern`                                      | Trimmed and non-empty when required.                                                                                      |
| `number`      | `integer` or `number`, `minimum`/`maximum`                                     | "int" in the tables means `integer`.                                                                                      |
| `money`       | `string`, `pattern: ^\d{1,10}\.\d{2}$`, bounds via `x-money-min`/`x-money-max` | Never a JSON number (§0.2). BDT. Fits `numeric(12,2)`. Needs change C4.                                                   |
| `bool`        | `boolean`                                                                      | Leaving it unset means "not stated". It doesn't mean false.                                                               |
| `select`      | `string` + `enum` of option codes                                              | Codes are snake_case and stable. Labels come from i18n.                                                                   |
| `multiselect` | `array` of `enum` strings, `uniqueItems`, `minItems: 1` when required          |                                                                                                                           |
| `date`        | `string`, `format: date`                                                       | A Dhaka calendar day (§13.15). Relative rules like "not in the past" are zod refinements.                                 |
| `phone`       | `string`, `pattern: ^\+880\d{7,10}$` (E.164 BD, landline allowed)              | Used only where a second number is part of the listing itself (a doctor's serial line). Never searchable or in analytics. |
| `textarea`    | `string`, `maxLength`                                                          | Multi-line free text (descriptions, menus). Same rules as text; never filterable or analytics-safe.                       |

**Reserved keys** (schema §4.2): `price` (money), `bedrooms` (int), `seats`
(int) and `area` (number, **square feet**) become generated columns for
range filtering, so they must use exactly these keys and types. `area` is
entered in square feet. Converting katha/decimal/shotangsho (schema.md §4.2)
isn't built yet; no category in this spec needs it.

**Conditional fields** use `x-show-when: { "field": "property_type", "in": ["flat", "house"] }`
on a property: the field is shown (and allowed) only while its controller, a
select, multiselect or bool, holds one of those values. A hidden field must be
absent (`field.not_applicable`), and a field listed in `required` is required
only while it is shown. Chains are allowed; cycles are rejected at publish.
The tables show these as "shown if …". Other conditional requirements ("req
if salary set") use JSON Schema `if`/`then` in `allOf`. Both are enforced by
the API and mirrored by the client form renderers (packages/dynamic-form,
apps/mobile/lib/core/dynamic_form).

**Numbers in validation rules** (bounds, lengths) are schema _data_ in
`category_field_schemas`, not application code, so hard rule 9 is satisfied.
"Current year" means the year at validation time, not a constant.

### 3.3 Flags

| flag             | meaning                                                                                                               | stored in                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| **F** filterable | A Meilisearch filter or facet. Selects, multiselects and bools become facets; numbers and money become range filters. | `filterable_fields`                           |
| **S** searchable | Included in full-text search along with `title`/`description` (for selects, the translated label is indexed).         | `searchable_fields`, a new column (change C3) |
| **C** card       | Shown on the list card after title, price and locality. At most 3 per category, in the order listed.                  | `ui_schema` (`card`)                          |
| **A** analytics  | Kept after a privacy scrub (§13.31). Never free text, phone or URL.                                                   | `analytics_fields`                            |

This widens the old rule that "filterable = enum fields only" to include bools
and numeric ranges. Meilisearch supports both.

### 3.4 Labels and i18n

The `label bn / en` values below are stored **as text** in `ui_schema.labels`
and `ui_schema.options`, not as i18n keys. A category schema is
platform-managed content that is published without a deploy, like
`categories.name_bn`/`name_en` (schema.md §13.12), so its labels can't live in
the client bundles. Bengali is the default locale; English is the fallback.
Validation errors are returned as stable codes (`field.required`,
`field.out_of_range`, …) with the field key as the path, and the clients
translate those codes.

### 3.5 Parents

`buy-sell` is the only parent. `gadgets-electronics`, `fashion`,
`second-hand-vehicles`, `construction-materials` and `home-living` are its children, all of
kind `marketplace` (the trigger requires a child's kind to match its parent's).
The parent's fields (`price`, `condition`) are merged into each child when the
child's schema is published (§13.13). **A child may narrow an inherited field
but never loosen it**: it can shrink the enum, make the field required, or
change the label key. Change C5.

A post placed directly in `buy-sell` is a general "other items" post with only
the parent's fields. Agriculture, livestock, homemade food and gas cylinder
stay top-level on purpose: each is a distinct home tile, and `condition` means
nothing for them.

### 3.6 Expiry, approval, monetization

- **Expiry:** a per-category default. It needs change C1, because today there is only the global `post_expiry_days_default` (30). Places never expire; they go stale and get re-verified instead. Module tables keep their own expiry rules.
- **Manual approval** = `default_moderation_mode_code = 'pre'`. Categories without it (NULL) follow the tenant's mode, which is `post` by default.
- **Monetization mode** is stored in `categories.monetization_mode_code` (migration 0018; platform admins edit it through the category CRUD). Each mode maps to a lever:

  | mode           | lever                                                                                                                                                                                                                                                                                |
  | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | `per_listing`  | `default_post_cost_credits > 0`                                                                                                                                                                                                                                                      |
  | `boost`        | Listing is free (`cost = 0`). Revenue comes from `boosts`.                                                                                                                                                                                                                           |
  | `subscription` | Regular sellers (dealers, operators, claimed businesses) are expected to buy a store plan. For post categories, `cost > 0` so casual posters pay per post, and plan members use `included_credits`. For places, a claimed owner's store plan pays for featured placement and offers. |
  | `lead_fee`     | Free to list. Revenue per revealed contact comes later (change C6).                                                                                                                                                                                                                  |
  | `free`         | No monetization.                                                                                                                                                                                                                                                                     |

- **Boost cost** is **global per boost type** (`boost_types.default_cost_credits`, which tenants can adjust within min/max). It is not per category. Boosting is available in every post category. For `boost`-mode categories it is the main revenue source. Per-category boost pricing was considered and dropped for now (Q3).
