# ADR 001: API client generation — OpenAPI, TypeScript, and Dart

**Status:** Accepted — amended 2026-09-24 (see "Amendment" at the end)
**Date:** 2026-09-23
**Package:** `packages/shared-types`

## Context

`apps/web`, `apps/admin`, and `apps/mobile` (Flutter) all need to call `apps/api` without
hand-maintaining request/response shapes in three places. The API already exposes an OpenAPI
document via `@nestjs/swagger` (`/api/docs`, `/api/docs-json`), so the spec is the natural
single source of truth — but two things had to be fixed first, and one thing was found and
deliberately left for later, all recorded here rather than silently worked around.

### The OpenAPI document was mostly empty

Request DTOs are built with a project-specific `createZodDto` helper
(`apps/api/src/common/pipes/zod-dto.ts`) that carries a zod schema at runtime for validation,
but until now declared no properties and had no `@ApiProperty`/`@ApiBody` decorators anywhere.
Every request body and query DTO therefore showed up in the spec as an empty `{}` schema —
generating a client from it would have produced request bodies typed as empty objects.

**Fix:** `createZodDto` now converts the zod schema to an OpenAPI schema (`zod-openapi.ts`,
in the same folder) and applies it as real `@ApiProperty` metadata on the generated class, for
every top-level shape key. This covers `@Body()` and `@Query()` DTOs alike (`@nestjs/swagger`
expands a `@Query()` DTO's own properties into individual query parameters). The zod schema
stays the single source of truth for both validation and docs — nothing about the
`class CreateThingDto extends createZodDto(schema) {}` pattern changes. Covered by
`zod-openapi.spec.ts` (schema conversion, unit-level) and `zod-dto.spec.ts` (a real
`SwaggerModule.createDocument()` call against a DTO shaped like the real `emailLogin`/`device`
schemas, asserting the exact resulting request-body schema).

Response types (`Promise<SessionTokens>` etc.) are plain TS interfaces returned from services,
not decorated DTO classes, so they still resolve to a generic `object` schema. The
`@nestjs/swagger` CLI plugin is now enabled (`apps/api/nest-cli.json`,
`compilerOptions.plugins: ["@nestjs/swagger"]`) since it's the standard, zero-dependency way to
infer response shapes from TS return types — but it only helps once those types are the plugin's
target shape (a class in a `.dto.ts`/`.entity.ts`-suffixed file, or similarly recognized).
**Response bodies in the generated clients are untyped (`unknown`/empty object) until that's
done** — a smaller, separate follow-up, not attempted here.

### The API didn't boot

Capturing a live spec meant running the API, which surfaced `TenantsService` and `AuthService`
depending on `SettingsService` without their modules importing `SettingsModule` (not `@Global()`)
— a pre-existing bug, unrelated to this change. Fixed by adding the import to
`tenants.module.ts` and `auth.module.ts`; verified with the full test suite plus a rebuild.

A second, deeper issue was found and **deliberately not fixed here**: `RbacModule`'s
`MeController` (and the `@RequirePermission`/`@RequireOwnership`/`@PlatformAdmin` decorators)
reuse `JwtAuthGuard` — a class provided by `AuthModule` and exported — via
`@UseGuards(JwtAuthGuard, ...)`. Even though `RbacModule` imports `AuthModule`, Nest fails to
resolve `JwtAuthGuard`'s own dependency (`TokenService`) at boot. Regular constructor injection
of an exported provider works fine across modules; this specific pattern — reusing another
module's provider as a guard _class reference_ in `@UseGuards()` — does not, at least not as
currently wired. This affects every route protected by `@RequirePermission`,
`@RequireOwnership`, or `@PlatformAdmin`, i.e. most of `RbacModule`. **Needs its own
investigation** — root cause wasn't confirmed (candidates: passing an instance instead of a
class to `@UseGuards()`, or re-declaring the guard as a local provider in each consuming
module) — tracked as follow-up work, not part of this change.

Because of this, the OpenAPI capture used to seed `packages/shared-types/openapi.json` was
generated by a throwaway script that registers the real controllers and DTOs with stub
providers (no DB/Redis), sidestepping both the boot bug and the lack of a Docker stack in some
environments. It reflects the real decorator metadata (routes, request/query schemas) for
every controller, including `RbacModule`'s, even though the app itself won't boot yet. Once the
`RbacModule` bug is fixed and a normal dev stack is available, regenerate for real (see
Workflow below) — nothing about the generation pipeline itself needs to change.

### The client apps don't exist yet

`apps/web`, `apps/admin`, and `apps/mobile` are still empty (no `package.json` /
`pubspec.yaml`) — this repo is earlier in "Week 3 — Client shells" than the phase description
suggests. This ADR and `packages/shared-types` are self-contained and don't depend on those
apps existing; wiring them in (adding `@amar-elaka/shared-types` as a workspace dependency in
`apps/web`/`apps/admin`, and a path dependency on `packages/shared-types/dart` in
`apps/mobile`) is a one-line addition once those shells are scaffolded.

## Decisions

### 1. Fetching the spec

> Superseded by the amendment: the spec is now captured offline, with no
> running API. Kept below as the original decision.

`packages/shared-types/scripts/fetch-openapi.ts` (`pnpm gen:fetch`) fetches
`{API_URL:-http://localhost:3000}/api/docs-json` from a **running** dev API and writes
`packages/shared-types/openapi.json`. It only talks to the local dev server — no auth, no
external network. `API_URL` overrides the host for CI or non-default ports.

### 2. TypeScript: `openapi-typescript` + `openapi-fetch`

- `openapi-typescript` turns `openapi.json` into a `paths`/`components` type tree
  (`src/types.generated.ts`, generated — never hand-edited).
- `openapi-fetch` is a ~6 kB runtime wrapper around `fetch` that reads those types to give
  `client.GET('/tenants/nearby', { params: { query: { lat, lng } } })`-style calls with the
  request/response bodies, path/query params, and status codes all typed from the spec — no
  code generation for the client itself, just the types.
- `packages/shared-types/src/client.ts` exports one hand-written function,
  `createApiClient(options)`, so `apps/web` and `apps/admin` each construct their own client
  with their own `baseUrl`/auth headers rather than sharing a singleton.

This pairing was chosen over alternatives (e.g. a fully generated SDK via
`openapi-generator`'s TS templates) because the project already writes REST calls by hand at
the call site — `openapi-fetch` keeps that style and only removes the "what's the shape of
this endpoint" guesswork, instead of imposing a generated-SDK abstraction layer.

### 3. Dart: hand-written models + `json_serializable`, not `openapi-generator`

Two real options, evaluated for a solo developer on a project whose API surface is still small
(Week 3: auth + tenant bootstrap only):

**`openapi-generator` (`dart-dio` template)**

- ✅ Fully spec-driven — regenerate on every API change, zero manual sync, same philosophy as
  the TypeScript side.
- ✅ Handles complex schemas (unions, discriminators) automatically as the domain grows
  (payments, credit ledgers, moderation).
- ❌ `openapi-generator-cli` is a JVM tool — adds a Java runtime as a dev-machine dependency,
  on top of the Node/pnpm/Flutter toolchains already required. CLAUDE.md already asks that new
  dependencies be deliberate; a whole second language runtime for one codegen step is a heavy
  ask for a solo developer.
- ❌ Generated code is generic/verbose and hard to customize (naming, nullability, immutability
  helpers) without maintaining custom Mustache templates — another thing to own.
- ❌ Black-box: generator bugs/version churn are harder to debug than reading a schema mismatch
  in a hand-written model.

**Hand-written models + `json_serializable`**

- ✅ Standard, minimal Flutter-native tooling (`json_annotation` + `json_serializable` +
  `build_runner`) — no JVM, nothing outside the Dart/Flutter ecosystem every Flutter developer
  already has.
- ✅ Full control over the Dart-side shape (naming, nullability, enums) — pairs cleanly with
  whatever state-management pattern `apps/mobile` ends up using.
- ✅ Incremental: only the models a screen actually needs get written, matching "Week 3, no
  business features yet" — no boilerplate flood from generating the entire spec upfront.
- ❌ Manual sync cost: a developer must update the Dart model by hand when the API DTO changes.
  Nothing catches drift automatically the way the TypeScript side's compiler does.

**Decision: hand-written + `json_serializable`.** The deciding factor is the JVM dependency,
not code quality — `openapi-generator` is a fine choice once the API surface and team are
larger and the sync cost dominates. The manual-sync risk is bounded today by the tiny surface
area, and revisiting this decision later (once `apps/mobile` exists and the surface has grown)
is cheap: nothing else in this ADR depends on the choice.

**Implementation:** `packages/shared-types/dart` is a standalone Dart package (own
`pubspec.yaml`), not nested inside `apps/mobile` (which doesn't exist yet) — once `apps/mobile`
is scaffolded, it depends on this package via a local path dependency
(`amar_elaka_api: {path: ../../packages/shared-types/dart}`), the same monorepo-shared-package
pattern `packages/shared-types` itself uses for the TS side. It ships three models mirroring
the real auth DTOs (`Device`, `EmailLoginRequest`, `SessionTokens`) as the pattern reference;
future models follow the same shape (a class + `@JsonSerializable()` + a `part '*.g.dart'`
directive), written by hand against the DTO/service source, not against `openapi.json`.

> Not verified against a live Dart build in this environment — the available Flutter SDK
> (`/mnt/c/flutter`, a Windows-side install) fails under WSL due to CRLF line endings in its
> shell scripts, unrelated to this change. Run `dart pub get && dart run build_runner build`
> once on a working Dart install to confirm and produce the `.g.dart` files.

### 4. Workflow

```
pnpm gen:api            # capture openapi.json from the API's code, generate TS types
```

No running API, database or Redis needed (see the amendment). `pnpm typecheck`, `pnpm lint`
and `pnpm build` regenerate `src/types.generated.ts` from the committed `openapi.json` on their
own, so a fresh clone works without running `gen:api` first.

Dart models are **not** part of `pnpm gen:api` — they're hand-written, so there's nothing to
regenerate from the spec. After hand-editing a model, run (inside `packages/shared-types/dart`):

```
dart pub get
dart run build_runner build --delete-conflicting-outputs
```

### 5. What's committed vs. generated

`packages/shared-types/openapi.json` is committed — it's the point of truth consumers diff
against in review. Everything derived from it is gitignored and rebuilt by the commands above:
`src/types.generated.ts` (TypeScript) and every `**/*.g.dart` (Dart). The hand-written sources
— `src/client.ts` and every non-`.g.dart` file under `dart/lib` — are committed as normal
source.

## Follow-ups (not done here)

1. Fix the `RbacModule`/`JwtAuthGuard` cross-module `@UseGuards()` boot bug (see above) —
   blocks the API from booting normally, not just this pipeline.
2. Type response bodies (currently generic `object`) — likely by turning the ad hoc
   `SessionTokens`/`MeResult`/`TenantConfig`/`TenantSummary` interfaces into real DTO classes
   the `@nestjs/swagger` plugin can see, mirroring what `createZodDto` now does for requests.
3. Wire `@amar-elaka/shared-types` (TS) and `packages/shared-types/dart` (Dart) into
   `apps/web`, `apps/admin`, `apps/mobile` once those shells are scaffolded.

## Amendment (2026-09-24)

Follow-ups 1 and 2 are done, and the capture no longer needs a running API. Details in
[ADR 021](021-web-admin-nextjs-apps.md); in short:

1. **The boot bug was a missing export.** A guard named in `@UseGuards()` is constructed in
   the _consuming_ module's scope, so `JwtAuthGuard`'s own dependency had to be resolvable
   there. `AuthModule` now exports `TokenService` alongside `JwtAuthGuard`. The API boots, and
   this also affected `StorageModule`'s `MediaController`, not only `RbacModule`.
2. **Response bodies are typed.** Each response shape the clients consume is one zod schema
   (`*/dto/*-responses.dto.ts`). The service's return type is `z.infer` of it, so the compiler
   proves the schema matches what is returned, and a `createZodDto` class carries it into
   `@ApiOkResponse`. `createZodDto` now also documents `.refine()`d objects (previously `{}`,
   e.g. `AssignRoleDto`), and the converter handles unions, literals and records.
3. **Offline capture.** `apps/api/src/openapi/capture-openapi.ts` creates the app in Nest's
   `preview` mode, which builds the module graph and reads controller/DTO metadata without
   instantiating any provider, so no connection is attempted. It runs from `dist/` (tsc output),
   never `tsx`, for the `design:type` reason above. `scripts/fetch-openapi.ts` is removed. The
   document definition is shared with `main.ts`, so the committed spec is exactly what the
   server serves at `/api/docs`.
